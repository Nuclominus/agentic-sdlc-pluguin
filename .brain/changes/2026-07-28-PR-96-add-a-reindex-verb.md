# PR #96 — add a reindex verb

> `feat` · merged 2026-07-28 · by @Nuclominus

## Summary

Two `brain-sync` follow-up PRs open at once both append a row to `_moc-changes.md`, so merging `develop` into the second one conflicts **every time**. That happened twice while merging #91/#94/#95 today.

The index is machine-owned, so the rule is to regenerate rather than hand-merge — but the only
regenerating verb was `sync --backfill`, which rewrites **every note from its PR** and destroys
exactly the enriched prose §2 of the rule requires each note to carry. So a one-line index conflict
cost either the hand-written half of the vault or a reach past the CLI into `buildChangesIndex()`,
which is what happened twice today.

## Changed areas

Repo-level only — no plugin under `plugins/` touched, nothing in the shipped payload changed.

- **`tools/brain-sync/cli.mjs`** — new `reindex` verb: rebuilds `_moc-changes.md` from the notes
  already on disk and touches nothing else. Reuses the existing `refreshIndex()` that `sync`
  already calls, so there is no second index-building path to drift.
- **`tools/brain-sync/test/cli.test.mjs`** — three cases: rebuilds from disk in
  reverse-chronological order (recovering a row a bad conflict resolution dropped), leaves note
  bodies **byte-identical** (the property `--backfill` violates, asserted directly), and is
  idempotent.
- **`.claude/rules/second-brain.md`** — §2 now names the two-open-PRs conflict and prescribes the
  fix (take `develop`'s index, run `reindex`, commit), with an explicit "never `--backfill` for
  this".

## Decisions & rationale

No ADR — this adds a missing verb to an existing tool rather than deciding a design.

- **Regeneration must not be all-or-nothing.** `sync --backfill` conflates two jobs: re-deriving
  notes from GitHub, and rebuilding the index. Only the second is ever wanted when resolving an
  index conflict, and coupling them made the safe operation carry the destructive one.
- **The verb is the fix, not a warning in the docs.** The rule already said "re-run the tool
  instead" for machine-owned content; the tool simply had no command that did the narrow thing. A
  documented hazard with no safe path is a trap, so the rule update ships with the verb rather than
  instead of it.
- Verified against the real vault as a no-op (60 notes, zero diff) — the expected behaviour of a
  faithful regenerator, and the cheapest possible proof it does not rewrite what it reads.
