# PR #153 — read the resolved plan once instead of discovering it

> `perf` · merged 2026-09-08 · by @Nuclominus

## Summary

A plan carrying a full stack profile exceeds the inline tool-output limit, so the harness saves it
to a file and hands the orchestrator a path. Nothing said what to do with one — and run 4 spent
five of its nine Steps 0→1d tool calls discovering the file's shape before it could read it
(`keys[]`, then `.prints[]`, then two subset projections), then invented its own
spill-to-scratchpad convention for the prompt blocks. That is procedure being re-derived per run,
which is exactly what [[decisions/ADR-0019-the-run-start-is-one-command]] exists to prevent.

| | run 2 | run 3 | run 4 |
|---|---|---|---|
| Steps 0→1d API calls | 6 | 6 | **9** |
| reached the saved-plan path | no | no | **yes** |

The regression is legible in the transcript, not statistical: the two runs that stayed at 6 never
hit the file path at all.

## What changed

Step **0-large** now states the read verbatim — one `jq` emitting `prints[]` followed by every
`CONTEXT` value in the key map, with `prompt_blocks` projected out and read one agent at a time at
3b-1. Verified against run 4's own plan file: **10,676 characters against 54,746.**

`plan.profile.role_expertise` is dropped with it. The merged, *unrendered* expertise map was
**17,910 of those 54,746 characters** — a third of everything the orchestrator carries before it
dispatches anything — and nothing read it. Its one documented consumer was a Step 5 telemetry field
that Step 5 never wrote; what expertise was in force is already identified by `primary_profile` +
`additive_profiles` + `plugin_version`, and `resolveExpertise` reads the in-process value rather
than this output. The rendered `prompt_blocks` remain the contract.

## Drift guard

The prescribed projection is now a contract with `resolvePlan`'s output, so a renamed plan key would
silently drop a `CONTEXT` value with every test still green — the same failure shape
[[decisions/ADR-0015-the-machine-value-invariant]] guards elsewhere. A test parses the projection out
of `SKILL.md` and asserts each name is a key the plan emits. Proven to bite: renaming `roots` →
`rootz` in the document fails with `0-large projects 'rootz', which resolvePlan does not emit`.

## What this does not show

The improvement is unmeasured — an argument from run 4's transcript, not a result. Only the next
run's `sdlc-lint start-window` settles whether removing the discovery returns to 6 or below, and the
H5-D2 DoD (2–3 calls) is still unmet on every run so far. The 60% orchestration overhead run 4 also
showed ($6.73 of $11.23, more than all eight agent phases combined) is a separate and larger
question, untouched here.
