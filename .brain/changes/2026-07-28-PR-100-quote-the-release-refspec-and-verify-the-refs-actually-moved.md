# PR #100 — quote the release refspec and verify the refs actually moved

> `fix` · merged 2026-07-28 · by @Nuclominus

## Summary

Step 6 of `/release` said:

```
git push origin <sha>:release
```

Under **zsh** — the operator's shell — `:r` is a parameter-expansion modifier that strips a file
extension, so `$SHA:release` expands to the SHA followed by a bare `elease` and the push fails with
`src refspec … does not match any`.

This bit the **v1.11.2** cut for real. The tag push on the very next line takes a literal argument
and succeeded, so the release came out half-applied: the `develop` bump moved, the tag `v1.11.2`
went out, and the `release` branch — the stable `@release` install channel — stayed on v1.11.1. It
was recovered only because the stderr happened to be read; unnoticed, step 7 would have published a
release announcing a version the stable channel never received. `--verify-tag` does not catch it:
the tag *was* fine.

## Changed areas

Repo-level only — `.claude/commands/release.md` is a maintainer command, not shipped in any plugin,
so nothing under `plugins/` and nothing in the marketplace payload changed.

- **Step 6** — the refspec is now written fully qualified and quoted, `"<sha>:refs/heads/release"`,
  with the SHA substituted literally rather than through a shell variable, and the zsh trap spelled
  out inline so the next edit does not quietly reinstate it. Followed by an explicit post-push
  check that `git rev-parse origin/release` equals the bump SHA.
- **Step 8** — the report now re-reads all four artifacts *from the remote* (`origin/develop`,
  `origin/release`, `git rev-list -n1 vX.Y.Z`, `gh release view`) and prints them, instead of
  restating what the commands were supposed to have done. All three refs must be the same SHA.
- Also corrects `gh release view --json isLatest`, which is not a real field — "latest" comes from
  `gh api repos/<owner>/<repo>/releases/latest`.

## Decisions & rationale

No new ADR — this applies an existing rule rather than deciding anything. Rule 4 of
[[decisions/ADR-0016-amend-the-spec-and-the-plan-together]] ("verify reported facts rather than
ledgering them") is exactly what step 8 was missing: it reported the intended outcome of a push
instead of reading the ref back.

- **A silent failure in a multi-step release is worse than a loud one.** The refspec bug was
  survivable; what made it dangerous was that the very next step succeeded and the summary reported
  success. Each step that moves a remote ref now has to prove it moved.
- **Fix the shell hazard at the source, not with a caution.** Fully qualifying and quoting the
  refspec makes the trap unreachable; the inline explanation exists so a future edit does not
  "simplify" it back.
- **Verification reads the remote, not local state.** A local `git log` can agree with a push that
  never landed; `git rev-parse origin/release` after a fetch cannot.
