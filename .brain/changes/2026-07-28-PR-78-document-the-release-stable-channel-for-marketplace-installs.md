## Decisions & rationale

**Two channels, and why a branch ref rather than a tag.** A marketplace added with a branch ref keeps
updating *from that ref*. `@release` therefore gives installs a line that only moves when a release
is deliberately cut, while the default `develop` install tracks every merge. The distinction is the
whole point: before this, everyone was effectively on bleeding edge whether they wanted it or not,
and a mid-review `develop` state could reach a user's machine.

**`/release` never force-pushes.** Every push in the flow must be a fast-forward; a rejection is
treated as "someone else moved the ref" and the command stops rather than reconciling. The failure
rule is explicit about partial state — it reports which of the three refs (develop bump, `release`,
tag) moved and which did not, so a half-finished release is legible instead of mysterious. The bump
runs in a temporary worktree so the operator's own checkout is never touched.

**The version bump deliberately skips the PR + brain-sync heartbeat.** A marketplace version bump is
a mechanical release artifact, not a change worth a change note — the notes describe what shipped,
and the release that ships them is not itself content.

**The warn-only per-plugin gate is the durable lesson here.** It flags any plugin whose content
changed since the last release without a `plugin.json` version bump. That check exists because the
failure had already happened: #77 shipped 32 files of G1 behavior under unchanged versions, and
because installed copies cache **by version**, the feature existed on `develop` and nowhere else
until #80 bumped them. Warn-only rather than blocking is the right severity — the operator may have
a legitimate reason, but they should never discover the omission after the release is out.
