# PR #195 — upgrade guide for 3.0.0, and drop a config key that does not exist

> `docs` · merged 2026-09-21 · by @Nuclominus

## Summary

Documentation prep for the v3.0.0 cut, held back at the `/release` step-4 confirmation — the second
time that gate paid for itself in one session (see [[changes/2026-09-21-PR-193-prepare-the-3-0-0-release-notes-and-bump-sdlc]]).

#190 had already brought `README.md`, `CONTRIBUTING.md` and `docs/` in line with embedded
frameworks; an audit confirmed no stale `*-plugin` reference survives outside `docs/plans/` run
artifacts. Two gaps remained. Nothing told a `2.x` user **what to do** about the upgrade — the only
upgrade note covered `1.x` → `2.0.0`, while `3.0.0` is the breaking release they are about to
receive on `@release`. And `docs/INSTALLATION.md` documented a first install only, with no page
anywhere describing how to update one.

The third finding is the substantive one. `CHANGELOG.md`'s `[3.0.0]` section claimed `stack` ids
remain valid in "`frameworks.enable/disable` keys in `.claude/sdlc.local.yaml`". **There is no such
key.** It was announced in a `1.x` release and did not survive the move of resolution into
`tools/resolve/` ([[decisions/ADR-0019-the-run-start-is-one-command]]): `applyLocalOverrides`
supports exactly `convention_skills_extra`, `cost_caps`, `extensions`, `extra_phase_prompts`,
`heal_checks`, `phase_command_overrides`, `post_pipeline_checks` and `skip_phases`, and nothing in
`plugins/sdlc/` reads an `enable` or `disable` key. It would have shipped in the public GitHub
release notes as a supported way to control framework activation.

That makes three factual errors caught in these release notes before publication — after "9 entries
to 3" (the real figure is 11 → 4) and the ten PRs the section omitted entirely. All three shared a
cause: the section was written inside the PR it describes, and checked against the prose asserting
the facts rather than against the refs and the code.

**The underlying gap is real and remains open.** A project carrying both Retrofit and Ktor receives
both sets of guidance, with no supported way to suppress one — the docs now say so plainly instead
of pointing at a key that does not exist. Worth an issue; deliberately out of scope for a
documentation pass whose job was to make the docs true before publishing.
