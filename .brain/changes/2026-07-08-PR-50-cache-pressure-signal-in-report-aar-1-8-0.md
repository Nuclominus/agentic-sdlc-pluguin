# PR #50 — cache-pressure signal in report + AAR (1.8.0)

> `feat` · merged 2026-07-08 · by @Nuclominus

## Summary

Track E's enabler (E5), built on the transcript-derived usage from 1.7.0/1.7.1. Turns the cache-read
finding (a real 7-phase run reads 6.65M cache tokens across 117 subagent turns) into a **tracked
per-phase metric**, so later cache-reduction work (E2 surgical reads, E1 trim floor) has a measurable
baseline and the AAR can flag heavy phases automatically.

At telemetry-enrich time, each phase now records `turns` (distinct API responses, deduped on
`message.id`, summed across passes), `peak_prefix_tokens` (largest single-turn cache-read, max across
passes), and a derived `cache_pressure` flag (`peak > 80k`, one exported constant; consumers read the
stored boolean). The HTML report renders a `cache <reads/turn>/turn · peak <peak>` subline under each
phase and a `High cache-pressure: <phase>` Signals entry (with ⚠) when flagged; `tools/aar/metrics`
adds those to `by_phase` plus a `cache_pressure_phases` list the analyst uses to target reduction.
`reads/turn` is derived at render, never stored; backward-compatible with pre-E5 telemetry. Smoke-
tested end-to-end on the real run (only the large-context `development` phase, peak 101k, trips).
