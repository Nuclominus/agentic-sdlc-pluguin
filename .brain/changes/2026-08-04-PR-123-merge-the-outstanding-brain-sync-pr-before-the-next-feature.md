## What changed

The rule described how to **repair** the two-brain-sync-PRs-open-at-once collision on
`_moc-changes.md` (take `develop`'s index, run `reindex`, never `--backfill`). It did not describe
how to **avoid** it, and avoiding it costs nothing:

> Merge the outstanding brain-sync PR **first**, then the feature PR.

The mechanism is why this is not merely a preference. Merging to `develop` triggers the Action,
which opens the next `brain-sync/pr-<n>` immediately — so an unmerged brain-sync PR does not sit
harmlessly. It becomes *two open at once* the moment the next feature PR lands, and the collision
stops being likely and becomes certain.

## Decisions & rationale

- _No ADR._ This records an operational ordering, not a design decision — it changes no structure
  and no tool behavior, only which of two already-documented moves you reach for first.
- **The repair bullet stays verbatim.** It is still correct once you are already in the collision,
  and the `--backfill` prohibition inside it is the sharpest line in the section: backfill
  regenerates *every* note from its PR and destroys enriched prose. The edit only labels which of
  the pair is prevention and which is repair.
- **Where the gap came from is the reusable part.** The rule was written while resolving a
  collision, so it recorded the resolution. Nothing was wrong with it; it was simply written from
  inside the failure, and a rule written there tends to describe the exit rather than the door you
  should not have walked through. Worth a second look at any rule whose provenance is an incident.
