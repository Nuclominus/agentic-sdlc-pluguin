# PR #166 — a path-loaded plugin discovers its own manifest, recipes and deps

> `fix` · merged 2026-09-20 · by @Nuclominus

## Summary

Closes #164. Cross-plugin discovery keys off `installed_plugins.json`, so a plugin loaded from a
**path** — `claude --plugin-dir`, `claude plugin eval`, any development checkout — was invisible to
*itself*. Every run halted at Step 0 with `Workflow 'default' not found. Available: (none)` while
`default.yaml` sat next to the code printing the halt, and `--stack=vanilla` reported "no installed
foundation declares that stack" of a stack that ships in the very plugin reporting it. A populated
cache masks it completely, which is why it survived normal use; it surfaced only when the
`plugins/sdlc/evals/` suite ran the orchestrator through the eval runner, which loads the plugin
under test from its path.

Four consumers were blind at once — manifests, `workflows/`, `runtime-dependencies.json` and skill
enumeration — so the fix folds the path root into the **installs map** once (`pathLoadedRoots` in
`roots.mjs`, `mergePathLoaded` in `manifests.mjs`, applied in `resolveProfile`) rather than teaching
each consumer about path loads.

## Decisions & rationale

- Implements [[decisions/ADR-0022-a-path-loaded-plugin-is-its-own-install]], which amends
  [[decisions/ADR-0009-plugin-root-resolution]]: ADR-0009 split reads into self-referential and
  cross-plugin, and a plugin's own manifest/recipes/dependencies fall on both sides.
- The signal is `CLAUDE_PLUGIN_ROOT` outside `/plugins/cache/` and nothing else. `ownPluginRoot()`
  was tried as a fallback and rejected: it names the checkout for *every* caller, including test
  fixtures and lint passes that never loaded the plugin. That was not a judgement call — it broke
  four existing plan tests by announcing this checkout to their synthetic consumers.
- Three of the six ADR decisions (replace *every* matching key, require a *declared* identity, treat
  a path load as enabled) came out of the **code review of this PR**, not the design. Each is a case
  where the first implementation did the locally reasonable thing and broke the property the ADR was
  written to establish. The enablement one was the sharpest: keeping the registered key so
  `enabledPlugins` would keep working meant that disabling the installed copy — the natural setup
  before running a checkout — vetoed the checkout and restored the original halt. Fixing only the
  manifest layer was *still* not enough; `discoverRecipes` and the dependency preflight apply the
  same veto, so `withPathLoadedEnabled` states the rule once for all four.
- Cost of the decision, recorded in the ADR: a path-loaded plugin can no longer be disabled from
  settings. Unloading it means not pointing the harness at it.
