# PR #86 — override a recipe's cost cap per project via sdlc.local.yaml

> `feat` · merged 2026-07-28 · by @Nuclominus

> Replaces #83, which GitHub auto-closed when its base branch (`fix/cost-cap-in-run-transcript-pricing`, the #82 branch it was stacked on) was deleted on merge. Same single commit `1d7a0a9`, now based directly on `develop` with #82 already in.

_(The auto-Summary above quotes the PR's opening note about branch mechanics, not the change itself.
What this PR actually does:)_ adds an optional `cost_caps` key to `<project>/.claude/sdlc.local.yaml`,
letting a project retune — or switch off — a shipped recipe's cost cap without shadowing the whole
recipe.

```yaml
cost_caps:
  android-feature: 8.00     # exact recipe name — wins over "*"
  "*": 5.00                 # fallback for any recipe with no exact entry
  hotfix: null              # explicit null = uncapped in this project
```

## Changed areas

- [[components/sdlc]] `1.12.0` → **`1.13.0`** — `cost_caps` parsed in Step 1b (new 1b-caps
  subsection) and applied in Step 1d-0; new telemetry field `cost_cap_source`; the HTML report
  labels an overridden cap.

## Decisions & rationale

Follow-up to [[decisions/ADR-0011-in-run-transcript-pricing-for-the-cost-cap]]: that ADR made the
caps *real*, which immediately made them worth tuning per project. No new ADR — this changes no
architecture, it closes an ergonomic gap the previous change created.

- **Why the key exists at all.** The only prior way to change one cap in one project was to shadow
  the entire recipe under `.claude/sdlc-workflows/` (RESOLVER.md Step 1) — duplicating the phase
  list, `heal:` and `loop:` blocks to change a single number, after which the copy silently stops
  receiving upstream recipe updates. That is permanent divergence as the price of one integer.
- **Applied only in Step 1d-0**, the single place the cap is resolved. The dry-run preview, the
  3d-cap gate and telemetry all already read `CONTEXT.cost_cap` from there, so they cannot disagree
  about which cap was in force. A lint test now asserts every `CONTEXT.cost_cap =` assignment lives
  in that section.
- **Own-key lookup, not truthiness.** `hotfix: null` is a deliberate opt-out and must override a
  shipped cap, while a missing key must not. Without that distinction a project could only ever
  tighten a cap, never loosen one.
- **The override replaces the recipe's number, never min/max with it** — a "safest of the two" rule
  would silently ignore half of what the project asked for.
- **Telemetry records the resolved cap plus `cost_cap_source`.** Recording the shipped default would
  leave a reader comparing spend against a cap that never applied — the same class of error as the
  `cap_status: "within"` that ADR-0011 exists to prevent.
- **Three of the new tests guard the spec, not the code**, since this is orchestrator-executed
  configuration: the key must appear in *both* 1b's table and 1d-0's resolution (a key that parses
  but is never consumed fails silently, which is worse than an absent one), 1d-0 stays the single
  writer, and exact name beats the `"*"` fallback. Two were verified to actually fail against a
  deliberately broken spec — the first draft of one was vacuous, satisfied by a subsection heading
  rather than the table row it meant to check.
