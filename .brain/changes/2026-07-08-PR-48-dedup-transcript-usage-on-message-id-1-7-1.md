# PR #48 — dedup transcript usage on message.id (1.7.1)

> `fix` · merged 2026-07-08 · by @Nuclominus

## Summary

Investigating *why so much cache was read* on a real 7-phase run surfaced a **measurement bug** in
the `tools/usage` cost tool shipped in #46 (1.7.0). Claude Code writes **one transcript line per
content block** of an assistant turn (a `thinking` block, each parallel tool call, …), and every one
of those lines repeats the **same** response-level `message.usage`. `extractUsage` summed usage
**per line**, so a single API response was counted once per block — inflating cache-read, billed
tokens, and `cost_usd` by ~2–4× (measured **2.35×**: 73 transcript lines for 31 real API calls; the
run read as `$16.87` was really `$5.41`).

Fix: `extractUsage` now dedupes on `message.id` (unique per API response) before summing — each turn
counted once, falling back to per-line counting only for lines with no id. Single fix point, so every
caller (`priceTranscripts`, `enrichTelemetry`, orchestration-overhead) is corrected. Added a
regression test with a multi-block turn; bumped `sdlc` 1.7.0 → 1.7.1. The affected consumer run was
re-enriched and its report regenerated with the corrected figures.

Once cost was measured accurately, the deduped anatomy (6.65M cache-read across 117 subagent turns —
~27% fixed boilerplate floor re-read every turn, ~73% accumulated context) motivated a new roadmap
track for cache-read reduction.
