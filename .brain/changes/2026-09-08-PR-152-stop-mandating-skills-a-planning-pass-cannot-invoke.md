# PR #152 — stop mandating skills a planning pass cannot invoke

> `fix` · merged 2026-09-08 · by @Nuclominus

## Summary

The first thing the mandate gate measured on a real run turned out to be mostly a defect in what
was being asked, not in what was done.

Run 4 (`child-profile-screen`, Little-One-Tracker, `sdlc` 2.2.0) scored `3b-1a-mandatory-skill` at
**16/23**. Adjudicating all eleven dispatches by hand, every one of the seven gaps was a `when`
trigger that could not fire: the development phase's planning pass, which writes a plan and no code
(3); a review-loop round that changed a view-model but edited no Compose UI (1); and a remediation
pass that edited two backup XML files (3). The rate on *applicable* mandates was **16 of 16**.

## What changed

`renderSkillsBlock` gains a `variant`, and the resolver emits `prompt_blocks[agent].skills_planning`
beside `skills` — the same rows, same dedupe, same order, framed as the obligations of the pass that
*follows*. 3b-special Pass 1 pastes that instead. The planning text deliberately carries no
`MANDATORY — invoke` token, which is the exact pattern the contract counts, so the denominator stops
counting a dispatch that cannot meet it. Both framings render from one argument object, so they
cannot disagree about which rows exist, and the unavailable-plugin downgrade WARN fires once.

The other two rows were left alone deliberately. `remediation` legitimately edits Kotlin on most
runs and a review-loop round legitimately edits Compose UI; their triggers were false *this time*,
not false by construction. Only the planning pass is structurally incapable of meeting them.

## The measurement now says what it is

The auditor cannot evaluate a natural-language `when`, so a mandate whose trigger never fired is
charged exactly like one that fired and was ignored. `matched/expected` is an **upper bound on
obligation**: a `partial` marks a run for adjudication, it does not establish non-compliance. Every
`every-mandate` contract now carries that caveat beside its number in `sdlc-lint compliance`, and
the orchestrator records run 4's decomposition as the worked example.

One further limit surfaced while adjudicating and is recorded rather than papered over: **the
contract is blind to order.** Run 4's review-loop round invoked `superpowers:test-driven-development`
at 13:26:35, after its two edits at 13:26:24 and 13:26:29. A `when` of "before your first
Write/Edit" is satisfied, as far as this measurement goes, by a skill invoked after the last one.
Presence is gated; sequence is gated nowhere.

## What run 4 did settle

It is the first run whose review loop actually ran, so it is the first test of #148's per-dispatch
triggers rather than an assumption about them. The review-fix dispatch invoked 2 of its 3 mandates —
against **0 of 3** for the same dispatch shape on run 1, before that fix — and the third was the
Compose-UI row its edits never touched. #148 holds.

## What this does not show

`skills_planning` has not run in a pipeline. It is verified by unit tests and by the adjudication
above, not by a measured run; the next run is what turns 16/23 into a number that means what it
says.
